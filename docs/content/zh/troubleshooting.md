# 排障与失败恢复

这一章的用法是：先按症状找到一行，再做那一行说的事。不要同时改三处配置——否则修好了也不知道是哪一处起的作用。

## 先做这三件事

```bash
bash deploy/manage.sh doctor   # 进程、目录、权限、监听
bash deploy/manage.sh logs     # 持续日志
```

第三件事：打开控制台的「服务 → 运行环境与保存位置」，点「复制诊断」，那里列出了工作目录、HOME、配置/消息/日志目录以及是否可写。

## 按症状查

### 打不开控制台

| 检查 | 命令 / 位置 |
| --- | --- |
| 进程在不在 | `docker compose ps` 或 `manage.sh doctor` |
| 端口对不对 | `manage.sh start` 会打印实际发布端口 |
| 绑定地址 | `deploy/.env` 里的 `BIND_ADDRESS`；远程服务器默认只听回环 |
| 防火墙 / 安全组 | 你的主机或云厂商设置 |
| 反代 | 是否指向 5099，`Host` 是否保留 |

### 能打开登录页但登录不了

| 现象 | 处理 |
| --- | --- |
| 密码错误 | 确认用的是控制台访问密码，不是 OneBot 令牌 |
| 一直要求 2FA | 用「使用恢复码」；恢复码也用完见 [首次启动](first-run.md#7-忘记密码或丢失-2fa) |
| 提示「协议状态加载失败」 | 服务端读协议失败；点「重新加载」，再查 `/api/agreements` 是否被代理拦截 |
| 登录后立刻被踢回 | 会话失效或多标签页互相覆盖；确认没有多个域名/端口交替访问 |

### 找不到 QQ 进程

| 检查 | 说明 |
| --- | --- |
| QQ 真的在跑吗 | Docker 里看 `manage.sh logs` 中 Xvfb/QQ 的输出 |
| 架构匹配吗 | 接入组件只支持对应平台架构 |
| 权限够吗 | Docker 需要 `SYS_PTRACE`；入口只给固定 UID 保留该能力 |
| Windows | 注意低完整性警告；账号检测依赖同机 QQ |

### 显示「等待登录」很久

QQ 里还没完成登录。去 QQ 窗口（或「打开 QQ 桌面」）完成扫码/验证，再点刷新。

### 「已在线」但机器人不工作

这是两个不同的层：

1. 账号层正常了。
2. 还要在「节点配置」里建端点、填对地址与令牌，并且机器人程序自己要正确处理消息。

按顺序核对：节点是否「未启用」→ 地址/端口/路径 → 令牌 → 机器人侧日志。见 [节点配置](onebot-config.md)。

### 保存后没生效

看保存状态芯片：

| 芯片 | 含义 | 处理 |
| --- | --- | --- |
| 已保存，下次连接时应用 | 账号不在线 | 先接入账号 |
| 已保存，但热重载失败 | 端点热切换失败 | 按错误信息改配置后重新保存 |
| 保存失败 | 什么都没写 | 读错误文本；常见是端口冲突或校验失败 |
| 未保存 | 改动还没提交 | 通用设置有防抖，等一下或点「保存」 |

服务级设置（端口、TLS、桌面入口、自动接入）保存后需要**重启程序**才生效，控制台没有替你做这件事。

### 日志不实时

| 检查 | 说明 |
| --- | --- |
| 状态点显示「重连中」 | SSE 断了，恢复后自动重连 |
| 反代缓冲 | 需要 `proxy_buffering off` |
| 反代读超时太短 | 至少给到 3600s |
| 服务端级别太高 | 「显示选项」里看服务端级别；文件级别由环境变量决定 |

### 桌面打不开

| 检查 | 说明 |
| --- | --- |
| 会话是否有效 | 退出登录/改密后桌面不能用，属预期 |
| `/desktop/` 是否被代理 | 路径要原样转发，且透传 WS 升级头 |
| `Origin` | 必须与当前访问主机匹配；换域名后旧页面会失败 |
| 入口被隐藏 | 「服务 → QQ 桌面」里端口为 0 且地址为空时入口不显示 |
| 外部桌面地址 | 外部服务自己负责认证，控制台会话不会自动带过去 |

### 重启后要重新扫码

见 [数据、备份与更新](data-backup.md#qq-的持久化与手动验证)。常见原因是卷没复用、HOME/XDG 被自定义启动方式覆盖，或用了 `down -v`。

### 界面错乱、点不到东西

1. 在地址后加 `?safe-mode=1` 打开控制台（跳过自定义 CSS）。
2. 进「高级 → 自定义 CSS」删掉或清空规则。
3. 还没好：进「高级 → 备份与重置」点「重置全部界面配置」（不可逆，会丢外观定制）。

### 提示仍显示旧数据

界面在读取失败时会保留上一次成功的数据，并明确标注。这类数据不能用来判断当前状态：先修读取，再看数字。

## 恢复阶梯

从轻到重，一级一级来：

1. **重试**：点界面上的「重试」「刷新」「重新连接」。
2. **重新保存**：把改动再保存一次，看错误是否变化。
3. **重启服务**：`bash deploy/manage.sh restart`。会中断机器人。
4. **重启 QQ**：卸载失败、管道僵死时用。QQ 侧会重新登录。
5. **排除界面因素**：`?safe-mode=1`。
6. **从备份恢复配置**：「服务 → 配置备份 / 恢复」。
7. **从备份恢复数据**：停服务 → 还原卷/目录 → 启动。
8. **重建环境**：仅在确认已备份的前提下。注意 `down -v` 会删除卷。

## 常见误判

| 说法 | 实际 |
| --- | --- |
| 「健康检查通过 = QQ 已登录」 | 健康检查只验证进程、桌面监听、控制台可访问 |
| 「端点正常 = 机器人能回复」 | 只说明监听或连接已建立 |
| 「本地目录还在 = 免扫码」 | 本地保留只避免重建环境，服务端是否接受会话由 QQ 决定 |
| 「日志里没报错 = 一切正常」 | 级别不够时错误也可能被过滤；TRACE 才有完整细节 |
| 「CI 绿了 = 所有平台都行」 | 只覆盖实际跑过的平台与场景 |

## 报告问题时

请提供：

- 「服务 → 运行环境与保存位置」复制的诊断（不含凭据）。
- 复现步骤与预期结果。
- 相关日志片段。**先删掉账号、令牌、消息内容和任何个人信息。**
- 平台、架构、版本号。

不要提供：QQ 密码、控制台密码、2FA 恢复码、真实抓包、账号数据库文件。
