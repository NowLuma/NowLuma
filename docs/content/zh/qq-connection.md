# QQ 连接

「QQ 连接」页（`/processes`）负责一件事：把接入组件装入**已经在你机器上运行的 QQ 进程**。它不启动 QQ，也不登录 QQ。

页面副标题写得很直接：「加载后，已登录账号将自动接入 OneBot」。

## 页面结构

| 区域 | 内容 |
| --- | --- |
| 卡片标题 | 「QQ 连接」+ 上面那句副标题 |
| 「打开 QQ 桌面」 | 仅在配置了桌面入口时出现；Docker 默认可用 |
| 排序 | 「PID」/「名称」/「状态」，只有多于一个进程时才显示；选择会被记住 |
| 「刷新」 | 重新读取进程列表；首次读取完成前不可点 |
| 进程卡片 | 头像（或 CPU 图标）、进程名、状态徽章、`PID {n} · QQ {uin}`、进程路径、错误行 |
| 操作区 | 「加载」或「卸载」，以及条件出现刷新图标 |

## 状态词与含义

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| 可加载 | 找到 QQ 主进程，尚未注入 | 点「加载」 |
| 加载中 | 正在注入 | 等待；期间按钮显示「加载中」 |
| 等待连接 | 已注入，等本地管道连上来 | 稍候；必要时点刷新图标重连 |
| 等待登录 | 管道已通，账号还没登录 | 在 QQ 窗口里登录 |
| 已在线 | 登录完成并被识别 | 可去「节点配置」建端点 |
| 错误 | 本次操作失败 | 看卡片上的错误行，见下方排障 |
| 已断开 | 曾经接入，现在断了 | 点刷新图标「刷新管道状态 / 重连」 |

刷新图标只在「已注入、连接中、已断开」时出现，作用是把管道状态查一遍并尝试重连。

## 加载一个账号

1. 自己启动并登录 QQ（或点「打开 QQ 桌面」在里面操作）。
2. 回到本页，点「刷新」确认能看到该进程，状态为「可加载」。
3. 点卡片上的「加载」。
4. 弹出「确认加载 Nowluma？」——这份确认会说明加载是**向该 PID 注入**接入组件。
5. 确认后等待状态变化。

**预期结果**：状态依次经过「加载中」→「等待连接」→「等待登录」→「已在线」，卡片上出现 QQ 号。顶部横幅会提示「正在向进程 {pid} 加载 Nowluma…」「已向进程 {pid} 注入 Nowluma，等待管道连接…」这类进行中信息。

**如果状态停在「等待登录」**：说明程序已经接上管道，但 QQ 里还没有登录。去 QQ 窗口完成扫码/登录，然后点「刷新」。

## 卸载

点「卸载」会弹出「确认卸载 Nowluma？」。这份确认的意义是：卸载可能让当前已建立的会话断开，机器人随之离线。

- 期间横幅显示「正在从进程 {pid} 卸载…」，完成后「已从进程 {pid} 卸载」。
- 如果卸载后管道仍然存活，会弹出单独的「卸载失败」窗口，建议「如需彻底卸载，请重启 QQ。」

**什么时候该卸载**：升级接入组件、排查冲突、或要让某个账号彻底离线时。日常开关机器人不需要卸载，去「节点配置」停用端点即可。

## 打开 QQ 桌面

「打开 QQ 桌面」是本项目里唯一与 QQ 登录直接相关的入口：它打开的是服务器上真实运行的 QQ 桌面，而不是一个模拟窗口。

| 事实 | 说明 |
| --- | --- |
| 认证 | 复用当前控制台会话（路径限定的 HttpOnly Cookie）。不把控制台令牌或 VNC 密码放进 URL |
| 后台 VNC | 仅监听容器内回环 `5900`，并保留独立密码认证；网关在服务器侧完成校验，不把该密码返回浏览器 |
| 端口 | Docker 只发布 5099 一个管理端口，**不再单独发布 6080** |
| 生命周期 | 退出登录、改密、会话失效后桌面不能再操作；空闲连接会关闭 |
| 外部桌面地址 | 可在「服务」里配置一个外部地址；它由外部服务自己的认证保护，不会自动获得控制台会话 |

二维码、短信验证、设备锁等全部在 QQ 自己的界面里完成。程序不会保存 QQ 密码，也不会伪造登录凭据。

扫码之后，去 **QQ 自己的设置**勾选自动登录。这一步只影响 QQ 自己，程序无法代劳。

## 示例：一台刚装好的 Docker 机器

1. 控制台首页点「打开 QQ 桌面」→ 在桌面里启动 QQ → 扫码登录 → 勾选自动登录。
2. 回「QQ 连接」，点「刷新」。
3. 卡片显示「可加载」，点「加载」并确认。
4. **预期结果**：几秒内变为「等待登录」，登录状态被识别后变为「已在线」，卡片显示 `PID 1234 · QQ 10001`（示例数字）。

Docker 部署默认开启 `hookAutoLoad`，即程序启动时自动尝试接入已打开且已登录的 QQ。它**不是** QQ 自动登录，也不会替你在 QQ 里扫码。

## 空状态、错误与旧数据

| 界面 | 触发条件 | 处理 |
| --- | --- | --- |
| 「未检测到可加载 QQ 主进程」+「启动 QQ 后刷新」 | 本机没有可接入的 QQ | 启动 QQ；Docker 里确认 QQ 真的在跑（`manage.sh doctor`） |
| 红色错误面板 +「重试」 | 读取进程列表失败 | 看待办错误信息；检查权限与容器状态 |
| 「…；当前显示上次成功读取的进程状态。」 | 本轮读取失败但有旧数据 | 数据是旧的，不要据此判断当前状态 |
| 卡片错误行 | 注入/卸载失败 | 记录错误文本，对照下表 |

## 排障

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 列表里根本没有 QQ | QQ 没启动、架构不匹配、容器里 QQ 已退出 | 先启动 QQ；Docker 看 `manage.sh logs` 里 Xvfb/QQ 的输出 |
| 一直「加载中」不动 | 注入被拒绝（权限/完整性） | Linux Docker 需要 `SYS_PTRACE`；Windows 注意低完整性警告 |
| 「等待连接」不前进 | 管道没连上 | 点刷新图标重连；仍失败看日志里桥接相关行 |
| 「已在线」但机器人收不到消息 | 这是两件事 | 去「节点配置」确认端点与令牌，见 [节点配置](onebot-config.md) |
| 卸载后仍提示失败 | 管道未完全退出 | 重启 QQ，再重新加载 |

## 保存与重启语义

| 动作 | 是否持久化 | 生效范围 |
| --- | --- | --- |
| 加载 / 卸载 | 否，是运行时状态 | 当前进程；程序重启后需重新接入（除非开启自动接入） |
| 自动接入已打开的 QQ | 是（服务设置） | 保存后**重启程序**生效 |
| 排序选择 | 是（页面偏好） | 立即 |
| 打开 QQ 桌面 | 否 | 当前浏览器标签 |

这里最容易被误解的一点：QQ 的自动登录设置保存在 QQ 自己的 HOME 里，和程序配置无关。Docker 保留整个 `/home/nowluma` 才能让设备状态延续；这仍然不保证 QQ 服务端一定接受会话。
