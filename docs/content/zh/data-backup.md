# 数据、备份与更新

这一章讲「哪些东西必须留着」「怎么备份」「怎么升级」「怎么确认没有被自己骗到」。

## 数据在哪里

### 原生运行

| 路径 | 内容 | 升级时 |
| --- | --- | --- |
| `config/` | 控制台密码/2FA、连接设置、运行与外观设置 | 保留 |
| `data/` | 账号消息库、媒体 | 保留 |
| `logs/` | 运行日志 | 保留 |
| QQ 自己的用户目录 | QQ 设置、凭据、用户存储、机器 ID | 不动 |

### Docker

| 卷 | 容器路径 | 内容 |
| --- | --- | --- |
| `nowluma_config` | `/app/config` | 控制台密码/2FA、连接、运行与外观 |
| `nowluma_data` | `/app/data` | 账号消息库与媒体 |
| `nowluma_logs` | `/app/logs` | 运行日志 |
| `nowluma_qq-home` | `/home/nowluma` | QQ 完整 HOME：设置、凭据、用户存储、机器 ID |

Compose 项目名固定为 `nowluma`，卷名不随源码目录变化。

### 两个不同的「备份」

| 备份 | 内容 | 在哪 |
| --- | --- | --- |
| 配置备份 | 程序配置（可选包含敏感凭据） | 「服务 → 配置备份 / 恢复」 |
| 界面配置备份 | 外观、布局、页面偏好、自定义 CSS | 「高级 → 备份与重置」 |
| 数据备份 | 消息库、媒体、日志、QQ HOME | 由你自己复制卷或目录 |

三者互不覆盖。**配置备份不含消息数据库**；界面配置备份连背景图片都不含。

## 备份

### 正确的顺序

1. 停止服务：`bash deploy/manage.sh stop`（原生则结束进程）。

   先停再备份，避免复制正在写入的 SQLite / WAL 文件。

2. 复制数据。Docker 用临时容器把卷内容导出，例如：

   ```bash
   docker run --rm -v nowluma_config:/src -v "$PWD/backup":/backup alpine \
       tar -czf /backup/config.tgz -C /src .
   ```

   四个卷（`nowluma_config`、`nowluma_data`、`nowluma_logs`、`nowluma_qq-home`）都要备。

3. 启动服务：`bash deploy/manage.sh start`。

4. 把备份文件放到别的地方（异机或对象存储）。备份和数据在同一块磁盘上不算备份。

### 配置备份的用法

「服务 → 配置备份 / 恢复」提供导出与恢复。两个勾选项分别控制「导出时是否包含敏感配置」和「恢复时是否一并恢复敏感配置」。

敏感内容包括：控制台会话状态、TLS 私钥、通知 URL、OneBot 令牌。恢复结果会明确列出「已恢复 N 项」「跳过 N 项（敏感配置，含 OneBot 配置）」「兼容转换 N 项」，并提示是否需要重启。

**跨版本恢复**：出现「兼容转换」说明备份来自旧结构，已被转换；转换后请自己核对关键项（端口、令牌、账号）。

## 清理数据

清理入口在「服务 → 存储管理」：

| 范围 | 前提 | 可撤销 |
| --- | --- | --- |
| 日志 | 无 | 否 |
| 文件传输临时数据 | 无 | 否 |
| 单个账号的某类数据 | 无 | 否 |
| 全部账号 | 所有账号离线 + 输入短语 `清理全部账号` | 否 |

清理前的自查：

- 这些东西还需要吗？
- 有没有做过备份，并且验证过备份能打开？
- 是不是只想腾空间？可以先只清日志和临时数据。

Docker 里另有一类常见误操作：`docker compose down -v`。它会删除全部卷，包括 QQ 的 HOME 和程序配置。普通 `stop` 不删卷；升级也不要用 `-v`。

## 升级

### Docker

```bash
git pull                    # 或替换源码目录
bash deploy/manage.sh start # 构建并启动，复用原卷
```

**预期结果**：`start` 等到健康检查通过后返回成功；原有账号、消息、外观设置和 QQ HOME 都在。

**失败时**：`bash deploy/manage.sh logs` 看构建或启动错误；数据卷没有被删，修好再 `start`。

### 原生

替换发行包内容，保留 `config/`、`data/`、`logs/`，重启程序。

### 升级前该做的

1. 备份（见上一节）。
2. 记录当前版本号（「关于」里有）。
3. 挑一个没人用机器人的时间：重启会断开所有已连接账号。

### 应用下载的更新

「关于 → 软件更新」检测到新版本时可以下载，就绪后显示「更新已就绪 · 重启后生效」，点重启会再确认一次。这个重启会中断所有连接的机器人。

如果显示「检查已关闭」，表示这个构建没有可用更新源；显示「无法检查」通常是源码运行或网络不可达。两者都不是「已是最新」。

## QQ 的持久化与手动验证

程序能做的只有：保留 QQ 的完整用户目录、固定的 HOME 与 XDG 配置目录、固定的主机名和第一次生成的机器 ID。它**不**重新生成凭据，也**不**替你登录。

因此：

1. 第一次在 QQ 窗口扫码登录，并在 **QQ 自己的设置**里勾选自动登录。
2. 重启服务验证：

   ```bash
   bash deploy/manage.sh restart
   ```

3. 打开「QQ 桌面」，看 QQ 是否自动恢复到登录状态。**不要只看控制台健康状态**——健康检查只说明进程和端口在，不说明 QQ 会话还有效。
4. 再执行一次 `stop` 和 `start`，验证容器重建后仍然如此。

可能的失败与含义：

| 现象 | 含义 | 处理 |
| --- | --- | --- |
| QQ 要求重新扫码 | 服务端会话过期、异地验证或风控 | 在 QQ 窗口完成验证；本地凭据帮不上 |
| 自动登录设置消失 | QQ HOME 卷没复用、HOME/XDG 被覆盖、用了 `down -v` | 检查卷挂载与启动方式 |
| 文件都在但仍要扫码 | 本地状态保留不等于服务端认可 | 这是正常情况，见上表第一行 |

自动化测试可以验证目录、设置标记、机器 ID 和接入链路，**但没有你的账号扫码，不会声称「真实 QQ 免扫码已验证」**。这也意味着：任何「保证不扫码」的说法都不成立。

## 迁移到另一台机器

1. 停止旧机器的服务。
2. 备份四个卷（或原生三个目录 + QQ 用户目录）。
3. 在新机器上安装并**先不要启动**。
4. 恢复卷/目录。
5. 启动并检查：「服务 → 运行环境与保存位置」里的目录是否可写；「关于」里的版本；账号是否需要重新扫码。

QQ 的设备与机器 ID 跟着 HOME 走，所以整个 HOME 都要一起迁移，只搬 `login.db` 不够。

## 恢复清单（出事时照这个顺序做）

1. 停服务。
2. 备份当前状态（哪怕它已经坏了，也先留一份）。
3. 从最近一次备份恢复配置 / 数据。
4. 启动，看日志。
5. 只改一个变量再试下一次，否则无法判断是哪一步修好的。

更多症状对照见 [排障与失败恢复](troubleshooting.md)。
